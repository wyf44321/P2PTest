## 2. 功能需求

### FR-001 STUN 公网地址获取

| 属性 | 值 |
|-----|---|
| 优先级 | P0 |
| 模块 | 客户端 - STUN 客户端 |

**描述**：App 启动后，自动通过 STUN 服务获取自身公网 IP 和端口，展示在界面顶部。获取过程中显示加载动画，获取失败时自动切换到 STUN 配置界面。

**处理流程**：
1. App 启动后，界面显示转圈动画 + 「正在获取公网地址…」提示文字
2. 检查本地是否有用户上次记录的 STUN 服务器，如有则优先使用
3. 依次尝试 STUN 服务器（用户记录的优先，然后是默认列表）
4. 获取成功：在界面顶部展示 `IP:Port`，进入主界面
5. 所有 STUN 服务器均获取失败：自动切换到 STUN 服务器配置界面

**验收标准**：
- [ ] App 启动后显示转圈加载动画和提示文字
- [ ] 优先使用用户上次记录的 STUN 服务器
- [ ] 顶部正确展示 IP:Port 格式的公网地址
- [ ] 支持点击复制地址到剪贴板
- [ ] 单个 STUN 失败自动尝试下一个
- [ ] 所有 STUN 失败时自动切换到 STUN 配置界面
- [ ] 网络切换后自动重新获取

| 优先级 | P0 |
| 模块 | 客户端 - STUN 客户端 / UI / 本地存储 |

| 自建 STUN 2 | 61.151.231.231:2312 |
| Google STUN | stun.l.google.com:19302 |
| Google STUN 1 | stun1.l.google.com:19302 |
| Google STUN 2 | stun2.l.google.com:19302 |

| Ekiga | stun.ekiga.net:3478 |
| IdeasIP | stun.ideasip.com:3478 |
| Schlund | stun.schlund.de:3478 |

**处理流程**：

### FR-005 监听用户列表展示

| 属性 | 值 |
|-----|---|
| 优先级 | P0 |
| 模块 | 客户端 - UI / 客户端 - 连接监控 |

**描述**：实时展示所有监听用户的连接状态和网络指标。系统采用轮询探测机制，每秒依次探测下一个监听用户，更新其连接状态。

**探测规则**：
- 系统每 1 秒探测一个用户（轮询），依次对列表中的用户发送探测请求
- N 个用户时，每个用户的有效探测间隔为 N 秒
- 探测到连接断开时，自动触发重试规则（见 FR-006）
- 重试全部失败后，该用户降级为每 1 分钟探测一次
- 降级探测期间如恢复连接，自动切回正常轮询

**展示信息**（每个用户项）：

| 字段 | 说明 | 示例 |
|-----|------|------|
| 地址 | 对方的 IP:Port | 203.0.113.42:12345 |
| IP 归属地 | IP 所属地理位置和运营商 | 上海市/电信 |
| 连接状态 | 当前连接状态 | ● 已连接 |
| 延迟 | RTT 值 | 45ms |
| 丢包率 | 近期丢包比例 | 0.2% |

**验收标准**：
- [ ] 正确展示所有监听用户
- [ ] 添加用户后自动查询并展示 IP 归属地
- [ ] IP 归属地查询中显示「查询中...」，查询失败显示「未知」
- [ ] IP 归属地信息缓存，避免重复查询
- [ ] 系统每秒依次探测一个用户（轮询），更新其延迟和连接状态
- [ ] 丢包率数据每 5 秒更新一次
- [ ] 连接状态变更时实时反映（颜色变化）
- [ ] 重连中的用户显示重连进度（如：重连中 3/5）
- [ ] 断开/失败的用户延迟和丢包显示「--」
- [ ] 降级监控中的用户显示「降级监控中（每分钟探测）」

### FR-006 断线重连

| 属性 | 值 |
|-----|---|
| 优先级 | P0 |
| 模块 | 客户端 - P2P 引擎 |

**描述**：检测到 P2P 连接断开后，按照梯度策略自动重连。

**重连策略**：

| 次数 | 间隔 |
|-----|------|
| 1 | 1 秒 |
| 2 | 5 秒 |
| 3 | 10 秒 |
| 4 | 30 秒 |
| 5 | 60 秒 |

**处理流程**：
- 轮询探测或 P2P 事件检测到连接断开后，自动开始梯度重连
- 重连成功：恢复「已连接」状态，切回正常轮询探测
- 重连失败（5 次用尽）：标记为「已断开」，降级为每 1 分钟探测一次
- 降级探测期间如恢复连接，自动恢复「已连接」状态，切回正常轮询

**验收标准**：
- [ ] 连接断开后自动开始重连
- [ ] 重连间隔符合梯度策略
- [ ] 重连过程中界面显示「重连中 (X/5)」
- [ ] 重连成功后恢复正常状态和数据展示
- [ ] 重连全部失败后标记为已断开，降级为每 1 分钟探测一次
- [ ] 降级探测期间恢复连接后自动切回正常轮询

### FR-007 延迟测量

| 属性 | 值 |
|-----|---|
| 优先级 | P0 |
| 模块 | 客户端 - 连接监控 |

**描述**：实时测量与监听用户的网络延迟（RTT）。

**实现方式**：
- 系统每秒依次探测一个用户（轮询），向其发送 Ping 包
- 对端收到后立即回复 Pong 包
- 本端计算 RTT = Pong 接收时间 - Ping 发送时间
- 展示最近一次测量的 RTT 值

**验收标准**：
- [ ] 延迟数据每次轮询到时更新
- [ ] 延迟值单位为 ms，保留整数
- [ ] 连接断开时延迟显示为「--」
- [ ] 延迟异常波动时数据仍正确

### FR-008 丢包率统计

| 属性 | 值 |
|-----|---|
| 优先级 | P0 |
| 模块 | 客户端 - 连接监控 |

**描述**：统计 P2P 连接的丢包率。

**实现方式**：
- 基于 Ping/Pong 机制，为每个 Ping 包分配序列号
- 统计最近 30 个 Ping 包中未收到 Pong 回复的比例
- 超过 3 秒未收到 Pong 即视为该包丢失
- 每 5 秒计算一次丢包率

**验收标准**：
- [ ] 丢包率每 5 秒更新一次
- [ ] 丢包率以百分比展示，保留一位小数（如 0.3%）
- [ ] 连接断开时丢包率显示为「--」
- [ ] 丢包率 0% 时正确显示

## 5. P2P 消息协议

客户端之间通过 UDP 直连交换消息。

### 5.1 协议标识

UDP 消息均为 JSON 格式，通过 `type` 字段区分消息类型。

### 5.2 消息类型

| 类型 | 方向 | 说明 |
|-----|------|------|
| `ping` | 双向 | 延迟测量请求，携带序列号和时间戳 |
| `pong` | 双向 | 延迟测量响应，回传序列号和请求时间戳 |

### 5.3 消息格式

所有消息使用 JSON 编码：

**Ping 消息**：
```json
{
  "type": "ping",
  "seq": 42,
  "timestamp": 1710000000000
}
```

**Pong 消息**：
```json
{
  "type": "pong",
  "seq": 42,
  "ping_timestamp": 1710000000000,
  "timestamp": 1710000000050
}
```

## 6. 状态机定义

### 6.1 P2P 连接状态

```
            打洞成功                     检测到断开
  [未连接] ─────────► [已连接] ─────────────────► [重连中]
     ▲                  ▲                           │  │
     │                  │          重连成功          │  │
     │                  └───────────────────────────┘  │
     │                                                 │
     │                  重连失败（5次用尽）              │
     │                          ┌───────────────────────┘
     │                          ▼
     │                  [降级监控中]
     │                     │  ▲ │
     │     降级探测恢复连接 │  │ │ 降级探测仍断开
     │       ┌─────────────┘  └─┘
     │       ▼
     │    [已连接] （切回正常轮询）
     │
     └──── 用户清除 / 手动删除
```

| 状态 | 显示 | 颜色 |
|-----|------|------|
| 未连接（Disconnected） | 已断开 | 红色 |
| 连接中（Connecting） | 连接中... | 黄色 |
| 已连接（Connected） | 已连接 | 绿色 |
| 重连中（Reconnecting） | 重连中 (X/5) | 橙色 |
| 降级监控中（DegradedMonitoring） | 已断开（每分钟探测） | 灰色 |
| 连接失败（Failed） | 连接失败 | 红色 |

### 6.2 STUN 获取状态

```
  [加载中] ──► [成功] ──► （网络切换）──► [加载中]
     │
     └──► [失败] ──► [配置中] ──► （重新获取）──► [加载中]
                        ▲
     （主动点击设置图标）──┘
```

| 状态 | 显示 |
|-----|------|
| 加载中（Loading） | 转圈动画 + 「正在获取公网地址…」 |
| 成功（Success） | IP:Port + 设置图标（⚙） |
| 失败（Failed） | 自动转入配置中状态 |
| 配置中（Configuring） | STUN 服务器配置界面（可选列表 + 自定义输入） |

## 7. 用例描述

### UC-001 启动 App 并获取公网地址

**参与者**：用户

**前置条件**：设备已联网

**主流程**：
1. 用户启动 App
2. 界面显示转圈动画 + 「正在获取公网地址…」
3. 系统检查本地是否有用户记录的 STUN 服务器，优先使用
4. 系统依次尝试 STUN 服务器获取公网 IP 和端口
5. 获取成功，加载动画消失，顶部展示公网地址 `203.0.113.42:12345`
6. 界面显示监听用户列表（从本地恢复或空列表）

**替代流程**：
- 4a. 所有 STUN 服务器均获取失败 → 自动切换到 STUN 配置界面（见 UC-001a）
- 4b. 用户在配置界面选择服务器并重新获取成功 → 继续步骤 5

---

### UC-001a 配置 STUN 服务器

**参与者**：用户

**前置条件**：STUN 获取全部失败，或用户主动点击公网地址卡片上的设置图标

**主流程**：
1. 系统展示 STUN 服务器配置界面
2. 界面显示默认可选的 STUN 服务器列表和自定义输入区
3. 用户从列表中选择一个 STUN 服务器（或手动输入自定义地址）
4. 用户点击「重新获取」
5. 系统将用户选择的 STUN 服务器持久化到本地
6. 系统使用新的 STUN 服务器尝试获取公网地址
7. 获取成功，自动进入主界面

**替代流程**：
- 3a. 用户手动输入的地址格式不合法 → 提示「请输入合法的服务器地址（host:port）」
- 6a. 使用新服务器仍然获取失败 → 提示「获取失败，请尝试其他服务器」，留在配置界面

---

### UC-002 添加监听用户并建立连接

**参与者**：用户

**前置条件**：App 已启动，公网地址已获取

**主流程**：
1. 用户点击「＋」按钮
2. 系统弹出添加用户对话框
3. 用户输入 IP `198.51.100.10` 和端口 `8080`
4. 用户点击「添加」
5. 系统验证输入合法性
6. 系统将用户添加到列表，状态为「连接中」
7. 系统发起 P2P 打洞
8. 打洞成功，状态变为「已连接」
9. 开始延迟和丢包率监控

**替代流程**：
- 5a. IP 格式不合法 → 提示「请输入合法的 IP 地址」
- 5b. 端口不合法 → 提示「端口号须为 1-65535」
- 5c. 已存在相同地址 → 提示「该用户已在监听列表中」
- 7a. P2P 打洞失败（超时 10 秒）→ 状态变为「连接失败」

---

### UC-003 删除监听用户

**参与者**：用户

**前置条件**：监听列表中已有用户

**主流程**：
1. 用户在某个用户项上左滑
2. 呼出红色「删除」按钮
3. 用户点击「删除」
4. 系统关闭与该用户的 P2P 连接
5. 系统从列表中移除该用户
6. 列表刷新

---

### UC-004 监听用户断线重连

**参与者**：系统自动

**前置条件**：某个监听用户处于「已连接」状态

**主流程**：
1. 网络波动导致 P2P 连接断开
2. 系统检测到断开，状态变为「重连中 (1/5)」
3. 等待 1 秒后尝试第 1 次重连
4. 重连失败，状态变为「重连中 (2/5)」
5. 等待 5 秒后尝试第 2 次重连
6. 重连成功，状态恢复为「已连接」
7. 延迟和丢包率恢复正常显示

**替代流程**：
- 6a. 5 次重连均失败 → 状态变为「已断开」，降级为每 1 分钟探测一次
- 6b. 降级探测发现连接恢复 → 状态自动变为「已连接」，切回正常轮询

---

### UC-005a 一键清除断开连接

**参与者**：用户

**前置条件**：监听列表中存在已断开或降级监控中的用户

**主流程**：
1. 用户在「监听用户」标题栏点击「清除断开」按钮
2. 系统弹出确认对话框「确定清除所有已断开的监听用户？」
3. 用户点击「确定」
4. 系统一次性移除所有已断开和降级监控中的用户
5. 关闭相关 P2P 连接资源，取消降级探测定时器
6. 列表刷新，本地持久化数据更新

**替代流程**：
- 1a. 无已断开用户 → 按钮置灰不可点击
- 3a. 用户点击「取消」→ 关闭对话框，不做操作
